# Database Design — Online Queue Application

Stack: PostgreSQL 17 · Laravel 13 · PHP 8.5

## Overview

The schema uses two tables. The existing Fortify `users` table is reused for
authentication and extended with an `is_admin` flag; a single `queue_entries`
table stores the whole queue line. No join tables are needed because there is
exactly one queue and each row is independent.

## ER Diagram (textual)

```
+-------------------+          +---------------------------+
|      users        |          |       queue_entries       |
+-------------------+          +---------------------------+
| id (PK)           |          | id (PK)                   |
| name              |          | code        (e.g. A-001)  |
| email (unique)    |          | position    (display order)|
| password          |          | status      (enum)        |
| is_admin (bool)   |          | served_at   (nullable)    |
| ...auth fields    |          | created_at / updated_at   |
+-------------------+          +---------------------------+
```

There is no foreign key between the two tables. A queue entry is not owned by a
user — customers are not authenticated. Keeping the queue self-contained makes
`next` / `prev` / `mark` trivial status transitions with no joins.

## Tables

### 1. `users` (reused from Fortify)

Stores administrators (and any regular users).

| Column | Type | Notes |
| --- | --- | --- |
| `id` | bigint PK | auto-increment |
| `name` | varchar | |
| `email` | varchar, UNIQUE | login identifier |
| `password` | varchar | hashed by Fortify |
| `is_admin` | boolean, default false | grants access to the admin panel |
| `email_verified_at` | timestamp, nullable | |
| `two_factor_*` | various, nullable | Fortify 2FA columns |
| `created_at` / `updated_at` | timestamp | |

**Justification:** instead of a separate `admins` table, a single flag on
`users` keeps one authentication system (Fortify login) and lets the admin
panel be protected by a tiny middleware that checks `is_admin`. This is the
simplest correct model for a course project and avoids duplicating auth.

### 2. `queue_entries` (the queue line)

| Column | Type | Notes |
| --- | --- | --- |
| `id` | bigint PK | auto-increment |
| `code` | varchar(10), NOT NULL | human label, e.g. `A-001` |
| `position` | integer, NOT NULL | display order (sort key) |
| `status` | varchar, CHECK constraint | `pending`, `calling`, `called`, `skipped` |
| `served_at` | timestamp, nullable | set when the number is completed |
| `created_at` / `updated_at` | timestamp | |

**Justification:**

- **Single table, no join:** there is one queue line; every ticket is one row.
  The "current number" is simply the single row with `status = 'calling'`, and
  the "queue list" is all rows ordered by `position`. Both queries are O(1)
  lookups on indexed columns — no relationships required.
- **`status` enum (enforced with a CHECK constraint):** the status lifecycle is
  strict and state-machine-like, so we constrain valid values at the database
  level to prevent corrupted data:
  `pending → calling → called` (with `skipped` as an escape hatch).
- **`code` vs `position`:** `code` is the human-facing ticket label (shown on
  the display), while `position` is a stable numeric sort key so the list order
  never changes even if codes contain letters.
- **`served_at`:** enables the `prev` (recall) feature — the last *served*
  ticket is found by ordering on `served_at`, and lets the report "how long did
  people wait" be computed later.

## CREATE TABLE statements (PostgreSQL)

```sql
CREATE TABLE users (
    id                      BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name                    VARCHAR(255) NOT NULL,
    email                   VARCHAR(255) NOT NULL UNIQUE,
    email_verified_at       TIMESTAMP(0) NULL,
    password                VARCHAR(255) NOT NULL,
    remember_token          VARCHAR(100) NULL,
    created_at              TIMESTAMP(0) NULL,
    updated_at              TIMESTAMP(0) NULL,
    two_factor_secret       TEXT NULL,
    two_factor_recovery_codes TEXT NULL,
    two_factor_confirmed_at TIMESTAMP(0) NULL,
    is_admin                BOOLEAN NOT NULL DEFAULT false
);

CREATE TABLE queue_entries (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    code       VARCHAR(10) NOT NULL,
    position   INTEGER NOT NULL,
    status     VARCHAR(255) NOT NULL DEFAULT 'pending',
    served_at  TIMESTAMP(0) NULL,
    created_at TIMESTAMP(0) NULL,
    updated_at TIMESTAMP(0) NULL,
    CONSTRAINT queue_entries_status_check CHECK (
        status IN ('pending', 'calling', 'called', 'skipped')
    )
);

-- Useful indexes
CREATE INDEX queue_entries_position_index   ON queue_entries (position);
CREATE INDEX queue_entries_status_index     ON queue_entries (status);
```

> These statements mirror what Laravel migrations produce on PostgreSQL
> (`php artisan migrate`). The app manages the schema via migrations; the SQL
> above is provided for the assignment submission.

## Relationships summary

- `users` and `queue_entries` have **no foreign key** (customers don't log in).
- The "active ticket" is a **row state** (`status = 'calling'`), not a relation.
- This design deliberately trades a normalized multi-table model for a simple
  state-machine model that satisfies every requirement with fewer moving parts.
